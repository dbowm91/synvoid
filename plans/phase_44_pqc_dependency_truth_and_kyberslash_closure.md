# Phase 44 Plan: PQC Dependency Truth and KyberSlash Closure

Status: detailed handoff plan.

Roadmap: `plans/runtime_truthfulness_security_publication_roadmap.md`.

Baseline: `03cec2235fb250e64c33f29b66258eeb0607cdbc`.

## Primary goal

Give the WASM proof-of-work ML-KEM path a security story based on implementation provenance and test evidence, not on a renamed package escaping an advisory key.

## Current state

`crates/synvoid-wasm-pow` currently depends on:

```toml
pqc_kyber_edit = { version = "0.7", features = ["kyber768", "zeroize"] }
```

and `Cargo.lock` resolves 0.7.2.

Repository docs/skills still associate this path with RUSTSEC-2023-0079 (KyberSlash). RustSec reports that the original `pqc_kyber` package has no patched upstream release and recommends moving to maintained alternatives. Because `pqc_kyber_edit` has a different package name, `cargo audit` matching the original package identifier is not a sufficient control.

The current API exposes the standard ML-KEM-768 wire sizes (1184-byte encapsulation key, 2400-byte decapsulation key, 1088-byte ciphertext), so migration to final FIPS 203 ML-KEM-768 should be investigated, not assumed compatible.

## Preferred outcome

Prefer migration to a maintained final-ML-KEM implementation rather than retaining a permanent renamed fork.

Candidate priority:

1. RustCrypto `ml-kem` (current maintained FIPS 203 implementation);
2. another maintained, vector-verified ML-KEM implementation if wasm32 compatibility or API constraints block RustCrypto;
3. retain `pqc_kyber_edit` only as a temporary exception with source-level proof of the KyberSlash fix and a dated removal condition.

Do not switch algorithms/parameter sets. Keep ML-KEM-768 unless a separate protocol version is introduced.

## Workstream A — Establish protocol compatibility requirements

Document what the WASM PoW consumer persists or sends:

- public/encapsulation key byte format;
- secret/decapsulation key byte format;
- ciphertext byte format;
- shared secret length;
- whether data generated by older releases must decapsulate after upgrade;
- whether this is ephemeral challenge state only.

If protocol data is ephemeral and never crosses upgrade compatibility boundaries, migration can be a direct backend swap.

If old/new interoperability is required, add an explicit algorithm/backend version tag before migrating. Never guess that Kyber-768 draft encoding is byte-compatible with final FIPS 203 ML-KEM merely because sizes match.

## Workstream B — Backend spike on wasm32

Create a small adapter/spike for the preferred backend.

Verify:

```bash
cargo check -p synvoid-wasm-pow --target wasm32-unknown-unknown
cargo test -p synvoid-wasm-pow --profile ci
```

and build through the project's actual wasm-pack/Trunk path if applicable.

Check:

- RNG/getrandom wiring under wasm32;
- no unexpected `std`/OS dependency;
- output sizes;
- zeroization behavior;
- bundle-size delta;
- no unsafe/native requirement incompatible with browser WASM.

## Workstream C — Known-answer and differential vectors

Add deterministic test seams that accept explicit randomness/seeds if the backend supports them.

At minimum:

- official FIPS 203 ML-KEM-768 vectors or backend-provided NIST vectors;
- keygen/encap/decap round-trip;
- modified ciphertext implicit-rejection behavior according to the chosen implementation;
- wrong-size input rejection at the SynVoid adapter boundary;
- no secret material in Debug/error output;
- browser/WASM round-trip test where practical.

If retaining the current fork, add a regression test or source/provenance guard specifically tied to the division/timing patch rather than only version `0.7.2`.

## Workstream D — Security metadata and advisory tooling

Update:

- `SECURITY.md`;
- `.opencode/skills/crypto_dependencies/SKILL.md`;
- `.opencode/skills/security_patterns/SKILL.md`;
- `architecture/wasm_pow.md`;
- dependency baseline/deny metadata if affected.

State one of:

- migrated to maintained ML-KEM implementation; original KyberSlash advisory no longer applies to the dependency graph; or
- temporary fork retained, with exact upstream base commit, exact mitigation commit/diff, owner, review date, re-audit date, and removal condition.

Add a repository guard that fails if `pqc_kyber` or `pqc_kyber_edit` is reintroduced without the corresponding security metadata.

Do not create a cargo-deny ignore for an advisory that the scanner cannot associate with the renamed package and call that coverage.

## Workstream E — Secret handling

Current adapter returns secret keys/shared secrets as ordinary `Vec<u8>`.

Evaluate whether the WASM API requires JavaScript-visible owned bytes. Inside Rust:

- use zeroizing containers for decapsulation keys/shared secrets where possible;
- avoid cloning secret material unnecessarily;
- redact errors;
- zeroize temporary secrets on drop.

If JavaScript must receive secret material, document that JS/WASM memory cannot provide the same drop/zeroization guarantees as native Rust and keep exposure lifetime minimal.

## Workstream F — Remove stale compatibility code/dependency

After migration:

- remove `pqc_kyber_edit` from the manifest/lockfile;
- remove compatibility comments naming "Kyber" when the code implements final ML-KEM unless historically necessary;
- update constants/types to FIPS 203 terminology (`encapsulation_key`, `decapsulation_key`) if doing so does not break the JS API; otherwise document compatibility aliases.

## Verification

```bash
cargo test -p synvoid-wasm-pow --profile ci
cargo check -p synvoid-wasm-pow --target wasm32-unknown-unknown
cargo deny check
cargo audit
cargo xtask verify
```

Run the actual frontend/WASM build used in release packaging.

## Acceptance criteria

- The backend's relationship to KyberSlash is proven by migration or explicit source provenance, not inferred from package name.
- ML-KEM-768 protocol compatibility is documented and regression-tested.
- wasm32 release build passes.
- security docs and dependency policy match the actual resolved package.
- secret handling does not regress.
- no stale advisory text claims both "no fix" and "fixed fork" without explaining which package/source is present.
